---
title: Idempotency
description: Prevent duplicate operations with the Idempotency-Key header.
---

Write operations in the Bitwage Partner API support idempotency. Use it to
retry safely after a timeout, a dropped connection, or a `5xx` response,
without creating a duplicate company, recipient, or payroll.

## How it works

Include an `Idempotency-Key` header with a unique value in your write
requests.

- **First request.** Bitwage runs the operation and stores the response with a
  hash of the request payload.
- **Same key, same payload.** Bitwage returns the stored response with the
  original status code. It does not run the operation again, so it doesn't
  repeat side effects such as provider calls or emails.
- **Same key, different payload.** Bitwage rejects the request with
  `idempotency-key-reused-with-different-payload`.

```bash
curl -X POST "https://api.sandbox.bitwage.com/api/companies" \
  -H "Authorization: Basic YOUR_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 6f1c2a52-0a9f-4a54-9b38-1a2f0f7d1c11" \
  -d '{
    "legal_name": "Acme Corp",
    "email": "admin@acme.com"
  }'
```

## Endpoints that use idempotency keys

A missing key returns `400` with `idempotency-key-required` on these endpoints.

| Endpoint | Notes |
|---|---|
| `POST /api/companies` | |
| `POST /api/companies/{company_id}/ubo` | |
| `POST /api/companies/{company_id}/ubo/kyc` | |
| `POST /api/companies/{company_id}/documents` | |
| `POST /api/companies/{company_id}/kyb` | |
| `POST /api/company/{company_id}/recipients/create` | |
| `POST /api/company/{company_id}/recipients/{recipient_id}/distribution` | |
| `POST /api/company/{company_id}/recipients/{recipient_id}/documents` | |
| `POST /api/company/{company_id}/recipients/{recipient_id}/kyc` | |
| `POST /api/company/payroll/create` | Required with API key authentication only. OAuth requests aren't checked. |
| `POST /api/company/workers/pay` | Alias of `/api/company/payroll/create`. It shares the same idempotency records. |
| `POST /api/vendor/payroll/quotes` | |
| `POST /api/vendor/payroll/documents` | |
| `POST /api/vendor/payroll` | |
| `POST /api/wallets/request` | |
| `POST /api/wallets/crypto-withdraw` | |
| `POST /api/wallets/travel-rule/{record_id}/submit` | |
| `POST /api/wallets/{account_id}/lightning-invoices` | Reusing a key returns `idempotency-key-reused` instead of the stored response. |

Other write endpoints, such as `POST /api/company/workers/invite`,
the Individual endpoint `POST /api/user/distribution`, and `PATCH` and `DELETE`
endpoints, don't
accept idempotency keys. Retrying them can fail or repeat the action. See
[Retrying safely](/guides/errors#retrying-safely) for how to check state
before you retry.

## Key scoping

Idempotency keys are scoped to your partner account and the endpoint. Using
the same key on two different endpoints doesn't conflict.

Bitwage compares the request payload. It doesn't compare headers or the order
of JSON keys.

## Errors

| Code | Status | Meaning | What to do |
|---|---|---|---|
| `idempotency-key-required` | 400 | The `Idempotency-Key` header is missing or empty. | Add the header and send the request again. |
| `idempotency-key-reused-with-different-payload` | 400 | You used this key with different data on this endpoint. `data.retryable` is `false`. | Use a new key for the new request. To retry the original request, send it unchanged. |

## What is stored

Only successful responses are stored. If a request fails, for example with a
`400` validation error or a `5xx`, Bitwage doesn't store a response for the
key, so you can fix the request and retry with the same key.

If a request times out and you don't know whether it succeeded, retry with the
**same key and the same payload**. You get the original result if it succeeded,
or Bitwage runs it if it didn't.

## Best practices

- Generate a UUID for each logical operation.
- Store the key with the operation in your system before you send the request.
  Reuse it for every retry of that operation.
- Never reuse a key for a different payload on the same endpoint. Create a new
  key instead.
- For payrolls, also set `external_id` so you can find the payroll later with
  `GET /api/company/{company_id}/payrolls?external_id=`.
